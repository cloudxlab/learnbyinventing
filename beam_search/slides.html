Part 1: Fair Coin Toss

Challenge (skip ahead if you can):

Write a Python function fair_coin() that returns "H" or "T" with equal probability (50/50). Then write biased_coin(p) that returns "H" with probability $p$.

Already got it? Skip to Part 3.

Let’s start with the simplest random event: a fair coin toss.

How would you simulate one in Python?

Python’s random module gives us random.random(), which returns a number between 0 and 1.

print(random.random())   # e.g., 0.1489...

If this number is less than 0.5, call it Heads. Otherwise, Tails.

Hint: compare random.random() to 0.5.

Let’s verify it’s fair. Flip 10,000 times and count:

results = [fair_coin() for _ in range(10000)]
h_count = results.count("H")
print(f"Heads: {h_count}, Tails: {10000 - h_count}")
# Should be roughly 5000 each

It won’t be exactly 5000 each time — that’s randomness. But it should be close.

def weighted_choice(items, probs):
    r = random.random()
    running_total = 0
    for item, p in zip(items, probs):
        running_total += p
        if r < running_total:
            return item
    return items[-1]

Part 4: Generating Text with an LLM

Challenge (skip ahead if you can):

Use an LLM API to get next-token probabilities for a prompt. Write generate_greedy(prompt, n) that always picks the highest-probability token to build a sentence word by word.

Got it? Skip to Part 5.

A large language model (LLM) does something remarkably simple:

Given some text, it predicts probabilities for the next token.

For example, given "The cat sat on the", an LLM might output:

TokenProbability
mat0.35
floor0.20
roof0.15
bed0.10
table0.08
……

The simplest strategy: always pick the most probable token. This is called greedy decoding.

Let’s simulate an LLM with a simple dictionary. In practice you’d call an API — but this lets us focus on the algorithm:

def fake_llm(prompt):
    """Return a dict of {token: probability} for the next word."""
    words = prompt.lower().split()
    last = words[-1] if words else ""

    table = {
        "the": {"cat": 0.30, "dog": 0.20, "bird": 0.10,
                "sky": 0.10, "mat": 0.08, "house": 0.07,
                "tree": 0.05, "rain": 0.05, "sun": 0.05},
        "cat": {"sat": 0.40, "slept": 0.20, "ran": 0.15,
                "purred": 0.10, "jumped": 0.10, "ate": 0.05},
        "sat": {"on": 0.50, "down": 0.20, "quietly": 0.15,
                "still": 0.10, "up": 0.05},
        "on":  {"the": 0.60, "a": 0.20, "top": 0.10,
                "my": 0.05, "its": 0.05},
    }
    if last in table:
        return table[last]
    # Fallback: uniform over some words
    fallback = ["the", "a", "and", "is", "was", "it"]
    return {w: 1/len(fallback) for w in fallback}

It works! But notice a problem — greedy decoding often gets stuck in loops. It always picks the same “best” token, so it repeats itself.

Also, it’s boring. Real language is varied. “The cat sat on the mat” is perfectly fine, but so is “The cat sat on the roof.”

Can we control how random the sampling is?

Part 6: Temperature

Challenge (skip ahead if you can):

Write softmax_with_temperature(values, T) where $T$ controls how “sharp” the distribution is. Test with $T = 0.1$, $T = 1.0$, and $T = 5.0$. Then use it to generate text.

Got it? Skip to Part 7.

We want a knob that controls randomness:

  • Low randomness: almost always pick the best token (like greedy)
  • High randomness: pick more adventurously from unlikely tokens

Remember softmax from the classification chapter?

$\text{softmax}(x_i) = \dfrac{e^{x_i}}{\sum_j e^{x_j}}$

It makes big values bigger and small values smaller.

What if we divided the values by a number $T$ before applying softmax?

$\text{softmax}(x_i / T) = \dfrac{e^{x_i/T}}{\sum_j e^{x_j/T}}$

What happens when $T$ is very small? Very large?

Before coding — think through these cases:

Suppose values are $(2, 5, 1)$.

  • $T = 1$: values become $(2, 5, 1)$ — normal softmax.
  • $T = 0.1$: values become $(20, 50, 10)$ — huge differences! Softmax will put almost all weight on the largest value.
  • $T = 100$: values become $(0.02, 0.05, 0.01)$ — tiny differences. Softmax will make them nearly equal (uniform).

So $T$ is a “temperature” knob:

  • $T \to 0$: “frozen” — always pick the best (greedy)
  • $T = 1$: standard sampling
  • $T \to \infty$: “melted” — pick uniformly at random

import math

def softmax_with_temp(values, T=1.0):
    scaled = [v / T for v in values]
    max_s = max(scaled)  # for numerical stability
    exps = [math.exp(v - max_s) for v in scaled]
    total = sum(exps)
    return [e / total for e in exps]

vals = [2, 5, 1]
print("T=0.1:", softmax_with_temp(vals, 0.1))
# [~0.000, ~1.000, ~0.000] — almost greedy
print("T=1.0:", softmax_with_temp(vals, 1.0))
# [0.047, 0.936, 0.017] — standard
print("T=5.0:", softmax_with_temp(vals, 5.0))
# [0.279, 0.443, 0.279] — nearly uniform

Hint 2: subtract the max before exponentiating to avoid overflow.

Part 7: The Problem with Greedy Choices

Challenge (skip ahead if you can):

Instead of keeping just one candidate sentence, keep the top $k$ candidates at each step, expanding each one with all possible next tokens, then keeping only the best $k$ overall. Write beam_search(prompt, n, k).

Got it? Skip to the end.

Consider this scenario. The LLM gives these probabilities:

Token A (0.6)Token B (0.4)
Then next:A→X (0.3)B→Y (0.9)
Total:$0.6 \times 0.3 = 0.18$$0.4 \times 0.9 = 0.36$

Greedy picks A first (0.6 > 0.4). But the path through B is twice as good overall (0.36 vs 0.18)!

The locally best choice isn’t always the globally best path.

How do we fix this without trying every possible sequence (which grows exponentially)?

The idea: instead of keeping one candidate at each step, keep the top $k$ best candidates.

At each step:

  1. Take your $k$ current candidates.
  2. For each candidate, try all possible next tokens.
  3. Score every extension: candidate’s score $\times$ new token’s probability.
  4. Keep only the top $k$ overall.

It’s like exploring a tree, but instead of one path (greedy) or all paths (exhaustive), you keep $k$ beams of light shining through the most promising branches.

This is called beam search, and $k$ is the beam width.

Let’s trace through an example with beam width $k = 2$.

Start: "the" (score = 1.0)

Step 1: expand “the” with all next tokens:

“the cat”$1.0 \times 0.30 = 0.30$
“the dog”$1.0 \times 0.20 = 0.20$
“the bird”$1.0 \times 0.10 = 0.10$
……

Keep top 2: “the cat” (0.30) and “the dog” (0.20)

Step 2: expand both candidates, score all extensions, keep top 2 again. The beam explores two promising paths in parallel!

def beam_search(prompt, n_tokens, beam_width=3):
    beams = [(prompt, 1.0)]

    for step in range(n_tokens):
        all_candidates = []
        for text, score in beams:
            probs = fake_llm(text)
            for token, p in probs.items():
                new_text = text + " " + token
                new_score = score * p
                all_candidates.append((new_text, new_score))

        all_candidates.sort(key=lambda x: x[1], reverse=True)
        beams = all_candidates[:beam_width]

    return beams

Hint 1: for each candidate, loop through all next tokens and compute new_score = score * p.

Hint 2: sort all candidates by score descending, then slice [:beam_width].

What do you notice?

  • $k = 1$ is exactly greedy decoding!
  • Larger $k$ finds better (higher-scoring) sequences.
  • But the improvement gets smaller as $k$ grows.

In practice, $k = 3$ to $k = 10$ works well. The computational cost grows linearly with $k$, so it’s a good trade-off between quality and speed.
