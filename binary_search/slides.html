Part 1: The Core Idea

Challenge (skip ahead if you can):

Without using math.log, ** with fractional exponents, or any built-in root/log function, write nth_root(x, n) and log_base(x, b) using only binary search. Both should be accurate to 6 decimal places.

Someone thinks of an integer between 1 and 1000. You can ask “Is it less than, equal to, or greater than X?”

If you always guess the middle of the remaining range, each guess halves the possibilities: 1000 → 500 → 250 → … → 1.

How many times can you halve 1000 before reaching 1? Write count_halvings(n):

def count_halvings(n):
    count = 0
    while n > 1:
        n = n // 2
        count += 1
    return count

print(count_halvings(1000))  # 10
print(count_halvings(16))    # 4
print(count_halvings(1))     # 0

Hint: loop while n > 1, halving each time and counting iterations.

You just computed $\lfloor \log_2(n) \rfloor$. This is why binary search needs only ~10 guesses for 1000 items, and ~20 for a million.

The key requirement: each guess must tell you which half to keep. This works whenever the function is monotone — always increasing or always decreasing.

We will use this one idea to compute square roots, cube roots, nth roots, and logarithms — without any built-in math functions.

def sqrt_binary_search(n, precision):
    low = 0
    high = max(1, n)
    while True:
        mid = (low + high) / 2
        if abs(mid * mid - n) < precision:
            return mid
        if mid * mid < n:
            low = mid
        else:
            high = mid

Quick Check: Why do we use high = max(1, n) instead of just high = n?

Answer: B. When n < 1, the square root is bigger than n. For example, $\sqrt{0.25} = 0.5$. Using high = n = 0.25 would exclude the answer.

def cuberoot_binary_search(n, precision):
    sign = 1 if n >= 0 else -1
    val = abs(n)
    low = 0
    high = max(1, val)
    while True:
        mid = (low + high) / 2
        cube = mid * mid * mid
        if abs(cube - val) < precision:
            return sign * mid
        if cube < val:
            low = mid
        else:
            high = mid

    low, high = 0, 1
    if x >= 1:
        while 10 ** high < x:
            high *= 2
    else:
        low = -1
        while 10 ** low > x:

    while high - low > 1e-12:

        if 10 ** mid < x:

        else:

Hint 2: once bracketed, the loop is the same as before: compare 10**mid vs x. Stop when high - low is tiny.

def log_base_n(x, n, tol=1e-7):
    if x <= 0 or n <= 0 or n == 1:
        raise ValueError("Invalid input")
    low, high = 0, 1
    if x >= 1:
        while n ** high < x if n > 1 else n ** high > x:
            high *= 2
    else:
        low = -1
        while n ** low > x if n > 1 else n ** low < x:
            low *= 2
    while high - low > 1e-12:
        mid = (low + high) / 2
        if (n ** mid < x) == (n > 1):
            low = mid
        else:
            high = mid
    return (low + high) / 2

Hint: when n > 1, n**mid < x means move low up. When 0 < n < 1, the function is decreasing — flip the comparison.

Change of Base Formula

The change of base formula says:

$$\log_b(x) = \frac{\log_a(x)}{\log_a(b)}$$

Verify with your function:

# log2(8) using base-10 logs:
# log10(8) / log10(2) should equal log2(8) = 3
result = log_base_n(8, 10) / log_base_n(2, 10)
print(result)  # ≈ 3.0

# Try more: log5(625) = log10(625) / log10(5)
result = log_base_n(625, 10) / log_base_n(5, 10)
print(result)  # ≈ 4.0

This means you only need one log function (say base 10) — you can compute any other base from it by dividing. That’s why most calculators only have log and ln.

Part 7: Bonus — Binary Search on Sorted Arrays

Everything so far searched a continuous range of numbers. The same halving idea works on a sorted array — and this is the version you will meet everywhere, from databases to Python’s bisect module.

The setup changes slightly:

  • lo and hi are indices into the array, not numbers
  • You stop when the indices cross, not at a precision

def contains(arr, x):
    lo, hi = 0, len(arr) - 1
    while lo <= hi:
        mid = (lo + hi) // 2
        if arr[mid] == x:
            return True
        elif arr[mid] < x:
            lo = mid + 1
        else:
            hi = mid - 1
    return False

print(contains([1, 3, 5, 7, 9, 11], 7))   # True
print(contains([1, 3, 5, 7, 9, 11], 4))   # False

Hint 1: start with lo = 0, hi = len(arr) - 1. Loop while lo ≤ hi.

Hint 2: mid = (lo + hi) // 2. If arr[mid] == x, found. If arr[mid] < x, move lo = mid + 1. Otherwise hi = mid - 1.

Checking each small ID against every huge ID costs $m \times n$ comparisons. Binary-searching each costs only $m \times \log(n)$ — for 10 small IDs in a million-item list, that’s 200 comparisons instead of 10 million.

def find_min_convex(arr):
    lo, hi = 0, len(arr) - 1
    while lo < hi:
        mid = (lo + hi) // 2
        if arr[mid] > arr[mid + 1]:
            lo = mid + 1
        else:
            hi = mid
    return arr[lo]

print(find_min_convex([10, 9, 8, 6.5, 4.1, 3.2, 2, 4, 4.5, 6]))  # 2
print(find_min_convex([5, 3, 1, 2, 4]))  # 1

Hint: if arr[mid] > arr[mid+1], you’re on the downhill slope — set lo = mid + 1. Otherwise hi = mid.

“Walk downhill until it stops going down” is exactly how gradient descent trains ML models — you will meet this idea again.

Quick Check: A sorted list has 1,000,000 elements. What is the maximum number of comparisons binary search needs?
